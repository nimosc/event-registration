# עיצוב: הפרדת מספר בקשת התשלום + עמודת סוג הגשה

**תאריך:** 2026-07-06
**סטטוס:** מאושר על ידי נועם

## רקע והבעיה

בזרימת שני-השלבים (בקשת תשלום → מסמך חשבונאי), המספר שמחולץ ממסמך **בקשת התשלום** נשמר בעמודת מספר החשבונית (`INVOICE_NUMBER_COLUMN_ID = "text_mm3p1e0e"`) בלוח החשבוניות. כתוצאה:

1. **דליפת מספר:** כשפותחים את מודל הקבלה, שדה "מספר חשבונית / קבלה" ממולא מראש במספר בקשת התשלום (`openAccountingModal(inv.id, inv.invoiceNumber)`).
2. **נתון שגוי ב-Monday:** עמודת מספר החשבונית מכילה את מספר בקשת התשלום במקום את מספר הקבלה/חשבונית מס.
3. **חוסר הבחנה בין סוגי הגשה:** אין דרך לדעת ב-Monday אם רשומה נוצרה מהגשה חודשית רגילה או מהגשה וולונטרית ("חסר במערכת?" / בדיקה ידנית).

## החלטות (מאושרות)

- שתי עמודות Monday חדשות בלוח החשבוניות (5097191457), **ייווצרו אוטומטית** דרך ה-API (`create_column`) על ידי סקריפט חד-פעמי, וה-IDs יוקשחו בקוד.
- עמודת סוג ההגשה תהיה **עמודת Status** עם שתי תוויות.
- **Backfill** לרשומות קיימות יתבצע במסגרת סקריפט המיגרציה הקיים.

## עמודות Monday חדשות

| עמודה | סוג | תוכן |
|---|---|---|
| מספר בקשת תשלום | Text | מספר המסמך שחולץ/הוזן בשלב בקשת התשלום |
| סוג הגשה | Status | `בקשת תשלום חודשית` / `בקשה לבדיקה` |

## שינויי התנהגות

### שלב בקשת תשלום (POST /api/invoices)
- המספר (מחולץ או ידני) נשמר ל**עמודת מספר בקשת התשלום** החדשה.
- עמודת מספר החשבונית (`text_mm3p1e0e`) נשארת **ריקה** בשלב זה.
- עמודת סוג ההגשה נכתבת ביצירה: `voluntarySubmission === true` → `בקשה לבדיקה`, אחרת `בקשת תשלום חודשית`.
- תווית השדה ב-UI במודלי בקשת התשלום: **"מספר בקשת תשלום"**.

### שלב מסמך חשבונאי (POST /api/invoices/accounting-document)
- ללא שינוי בכתיבה: המספר של הקבלה/חשבונית נשמר לעמודת מספר החשבונית.
- **מודל הקבלה נפתח עם שדה מספר ריק** — `openAccountingModal` לא מעביר יותר את `inv.invoiceNumber` כברירת מחדל. השדה מתמלא רק מחילוץ הקבלה או ידנית.
- אימות מספר הקבלה מול המספר שחולץ נשאר כמו היום.

### Backfill (בסקריפט המיגרציה הקיים)
לכל רשומה בלוח החשבוניות:
- **סוג הגשה:** תיאור שמתחיל ב-`הגשה ידנית — חסר במערכת` → `בקשה לבדיקה`; אחרת → `בקשת תשלום חודשית`.
- **מספר בקשת תשלום:** רק לרשומות בסטטוס `הוגשה בקשת תשלום` (כולל רשומות פטור שהמיגרציה ממירה) — העברת הערך מעמודת מספר החשבונית לעמודה החדשה + ריקון עמודת מספר החשבונית. רשומות בסטטוס `הוגש מסמך חשבונאי` לא נגועות (המספר שם הוא של הקבלה).

## קבצים מושפעים

- `src/lib/monday.ts` — קבועים לעמודות החדשות; `createInvoiceItem` מקבל `paymentRequestNumber` ו-`submissionType`.
- `src/app/api/invoices/route.ts` — ניתוב המספר לעמודה הנכונה + כתיבת סוג הגשה.
- `src/app/invoices/InvoicesClient.tsx` — תווית "מספר בקשת תשלום"; פתיחת מודל קבלה עם שדה ריק.
- `scripts/migrate-exempt-invoices-to-payment-request.ts` — הרחבת ה-backfill.
- סקריפט חד-פעמי ליצירת העמודות (או שלב בתוך סקריפט המיגרציה) שמדפיס את ה-IDs.

## בדיקות ואימות

1. `npx tsc --noEmit` + `npm run build`.
2. הגשה חודשית בדפדפן: מספר בקשת התשלום נשמר בעמודה החדשה; עמודת מספר החשבונית ריקה; סוג הגשה = חודשית.
3. הגשה וולונטרית: סוג הגשה = לבדיקה.
4. פתיחת מודל קבלה לרשומה שהוגשה לה בקשת תשלום: שדה המספר ריק.
5. העלאת קבלה: המספר נשמר בעמודת מספר החשבונית.
6. הרצת מיגרציה dry-run: דוח backfill נכון לפני apply.
